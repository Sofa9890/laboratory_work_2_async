# Как понять и защитить лабораторную по asyncio

## Что мы моделируем

`sleep` здесь изображает ожидание ответа базы данных. Мы не ускоряем базу и не выполняем тяжёлые вычисления параллельно: пока один запрос ждёт, программа может начать обслуживать другие. Вся демонстрация работает на одном потоке event loop.

## В каком порядке запускать

Откройте проект в PyCharm и запускайте файлы из папки `starter` по одному:

1. `step1_sync.py` — примерно 10 секунд;
2. `step2_sequential.py` — тоже примерно 10 секунд (промежуточный шаг 2а);
3. `step2_async.py` — примерно 1 секунда (итог шага 2б);
4. `step3_server.py` — примерно 7 секунд;
5. `step3_server_async.py` — примерно 5 секунд.

В терминале из корня проекта: `.venv/bin/python starter/step1_sync.py`. Вместо имени файла подставьте любой из остальных. Никаких сторонних библиотек для этой работы не требуется.

## Шаг 1: `step1_sync.py` по строкам

- `import time` подключает стандартный модуль со `sleep`.
- `from timer import print_time` берёт готовый измеритель длительности из задания.
- `def work(n: int) -> None` определяет обычную, синхронную функцию для номера `n`; `-> None` означает, что она ничего не возвращает.
- `print(f"start {n}")` показывает начало работы. Буква `f` вставляет число `n` в текст.
- `time.sleep(1)` блокирует этот поток примерно на секунду: следующая строка и следующая задача пока не выполняются.
- `print(f"done {n}")` показывает конец ожидания.
- `def main() -> None` собирает сценарий.
- `for n in range(1, 11)` перебирает числа от 1 до 10; правая граница `11` не включается.
- `work(n)` полностью заканчивается до следующего витка цикла. Поэтому десять ожиданий складываются.
- `if __name__ == "__main__"` запускает код ниже только при запуске этого файла, а не при импорте.
- `with print_time(): main()` измеряет время исполнения `main` и печатает его при выходе из блока.

## Шаг 2а: `step2_sequential.py` по строкам

- `import asyncio` подключает стандартную библиотеку асинхронности.
- `async def work(n: int)` определяет корутину. Вызов `work(n)` сам по себе лишь создаёт объект корутины.
- `print(start)` показывает начало задачи.
- `await asyncio.sleep(1)` приостанавливает эту корутину и отдаёт управление event loop на секунду, не блокируя поток.
- `print(done)` выполняется после возобновления корутины.
- `async def main()` тоже корутина, поскольку внутри есть `await`.
- `for ...: await work(n)` **ожидает завершения каждого** вызова до начала следующего. Поэтому весь шаг всё ещё занимает около 10 секунд.
- `asyncio.run(main())` создаёт event loop, выполняет `main` и завершает loop.

Если удалить `await`, тело `work` не запустится: появится предупреждение `coroutine was never awaited`. Этот опыт описан в `answers.md`, а итоговый код оставлен рабочим.

## Шаг 2б: `step2_async.py` по строкам

- `work` такой же, как в шаге 2а: начало → неблокирующее ожидание → конец.
- `coroutines = [work(n) for n in range(1, 11)]` создаёт десять объектов корутин. Это выражение со списком ещё не выполняет их тела.
- `await asyncio.gather(*coroutines)` передаёт все десять корутин event loop и ждёт их общего завершения. Звёздочка раскрывает список в отдельные аргументы `gather`.
- Каждая корутина печатает `start` и уступает управление на `await asyncio.sleep(1)`. Loop запускает следующую. Поэтому все десять секундных ожиданий перекрываются, и общее время около одной секунды.

## Шаг 3а: `step3_server.py` по строкам

- `from timer import log, print_time`: `log` печатает прошедшее время рядом с сообщением, `print_time` — итоговое время.
- `CLIENTS` — список пар `(имя, длительность ожидания)`. У `bob` пять секунд, у остальных по полсекунды.
- `handle_request(client, duration)` изображает обработку одного обращения.
- Первый `log` отмечает приём запроса; `time.sleep(duration)` блокирует поток; второй `log` отмечает отправку ответа.
- В `main` цикл `for client, duration in CLIENTS` распаковывает каждую пару.
- `handle_request(...)` завершается до начала следующего клиента. Поэтому `bob` задерживает `carol` и остальных. Время складывается: `0.5 + 5 + 0.5 + 0.5 + 0.5 = 7` секунд.

## Шаг 3б: `step3_server_async.py` по строкам

- Данные `CLIENTS` те же самые: сравнение честное.
- `async def handle_request(...)` превращает обработчик в корутину.
- `await asyncio.sleep(duration)` изображает ожидание базы без блокировки event loop.
- `coroutines = [handle_request(client, duration) for ...]` создаёт пять корутин.
- `await asyncio.gather(*coroutines)` запускает их конкурентно и ждёт всех.
- Все клиенты получают «запрос принят» почти сразу. Через 0.5 секунды отвечают четверо быстрых клиентов, а `bob` — через 5 секунд. Общее время определяется самым длинным ожиданием, около 5 секунд.

`timer.py` уже был дан преподавателем: `monotonic()` измеряет прошедшее время, `log` печатает отметку, а `print_time` печатает итог после блока `with`. `step4_blocking.py` — дополнительное задание, для зачёта шагов 1–3 оно не требуется и здесь не выполнялось.

## Короткий текст для защиты

«Мы сравнили последовательное и конкурентное ожидание. Сначала десять вызовов `time.sleep(1)` заняли десять секунд. Затем мы использовали `asyncio.sleep`, но оставили `await` в цикле: время осталось тем же, потому что следующая работа не начиналась до завершения предыдущей. После `asyncio.gather` все десять корутин запускались вместе, и ожидания перекрылись: получилось около секунды. На модели сервера синхронная версия задерживала следующих клиентов за медленным `bob` и работала семь секунд. Асинхронная версия принимала все запросы сразу: быстрые клиенты отвечали через полсекунды, `bob` — через пять секунд. Сам запрос `bob` быстрее не стал; мы убрали ожидание очереди у других клиентов. Корутина переключается в точке `await`, когда управление получает event loop».
